<threat_model>
ASVS Level: 1
Block on: high severity threats

- Threat T-02-03: Score tampering or out-of-bounds score evaluation resulting in unauthorized payment authorization (e.g. negative scores or scores > 100).
  - ASVS Control: V11.1.1 (Business Logic - bounded scoring preventing integer/float overflow or bypass).
  - Mitigation: `TrustScorer` applies strict clamping `round(max(0.0, min(100.0, raw_score)), 1)` and deterministic decision boundaries: ALLOW (>=70.0), REVIEW (40.0-69.9), DENY (<40.0).

- Threat T-02-04: False positive denial of service against benign buyers sharing public Wi-Fi or ISP /24 subnets.
  - ASVS Control: V11.1.2 (Business Logic - false-positive mitigation against innocent users on shared infrastructure).
  - Mitigation: Citing D-06, direct identifiers (email, device, upi) carry 100% neighbor penalty weight while connections through IP subnets carry 50% penalty weight. Citing D-05, repeat buyers with clean histories receive up to +5 reputation bonus.

- Threat T-02-05: Coordinated multi-merchant fraud syndicates rotating credentials across merchants to evade merchant-level limits.
  - ASVS Control: V11.1.3 (Automated Threat Detection - detection of distributed multi-account syndicate operations).
  - Mitigation: `detect_rings_in_subgraph()` evaluates connected components across >=2 distinct merchants with average degree >=1.5 and >=1 failure, immediately isolating the ring and assigning score 0 to all member nodes.

- Threat T-02-06: Ring identifier churn across polling intervals obscuring audit tracking in merchant dashboards.
  - ASVS Control: V8.3.1 (Sensitive Data & Integrity - consistent audit tracking without ID drift).
  - Mitigation: Citing D-12, when subgraphs connect or expand, the oldest canonical UUID is preserved and propagated across all constituent nodes.
</threat_model>

<action>
1. Create `trust-graph-service/app/engine/scoring.py` implementing `TrustScorer`:
   - Implement static method `score_fingerprint(graph_manager: Any, fingerprint: dict[str, Any], merchant_id: str, request_id: str | None = None) -> dict[str, Any]`.
   - Initialize `base_score = 100.0`, empty `risk_factors` list, and `score_breakdown` dictionary matching `ScoreBreakdown` schema.
   - Step 1: Missing Signal Penalty (D-08). Count non-null signals in fingerprint. If count < 3, calculate missing count `3 - count`, penalty `-5.0 * missing`, deduct from `base_score`, update breakdown `missing_signals_penalty`, and record risk factor `"partial_fingerprint: N expected signal(s) omitted"`.
   - Step 2: New Entity Penalty vs Progressive Trust (D-05). Look up matched nodes in graph. If no nodes exist, apply `-10.0` penalty, record risk factor `"new_entity: no transaction history on record"`. If nodes exist, sum `successful_transaction_count` and `failed_transaction_count`. If both are 0, apply `-10.0` penalty. If total successful transactions >= 2, drop new entity penalty to 0.0. If total successful transactions >= 5 and 0 failed transactions, add reputation bonus `+5.0` (capped at 100.0).
   - Step 3: Known Fraud Node Penalty. If any matched node has `is_known_fraud == True`, apply direct fraud penalty: `-80.0` for direct identifiers (email, device, upi, ua) or `-40.0` for IP subnet (D-06). Record risk factor `"known_fraud_node: matched signal is directly flagged for fraud"`.
   - Step 4: 1-Hop and 2-Hop Fraud Neighbors with Tiered Subnet Weighting (D-06). Traverse 1-hop neighbors of matched nodes. Collect set of fraud neighbors. If any connection or neighbor is exclusively IP subnet, set `tier_weight = 0.5`, else `1.0`. For 1-hop: penalty `-40.0 * tier_weight * min(len(one_hop_fraud), 1)`. For 2-hop: penalty `-20.0 * tier_weight * min(len(two_hop_fraud) / 3.0, 1.0)`. Update `score_breakdown["fraud_neighbor_penalty"]` and add risk factors.
   - Step 5: Sliding Velocity Penalties (D-07). Inspect transactions on matched nodes within sliding 60-minute window (`t >= now - 60m`). Deduplicate transactions by `tx_id`. If `velocity_60min > 10`, apply `-25.0` penalty; else if `velocity_60min > 5`, apply `-10.0` penalty.
   - Step 6: Cross-Merchant Spread Penalties. Count distinct merchants seen across matched nodes within sliding 24-hour window (`t >= now - 24h`). If merchants > 5, apply `-35.0` penalty; else if merchants > 3, apply `-15.0` penalty.
   - Step 7: Ring Membership Penalty (D-12). If any matched node has `ring_id is not None`, apply `-100.0` penalty, override score to 0.0, and record risk factor `"ring_member: node is confirmed member of fraud ring {ring_id}"`.
   - Step 8: Exponential Half-Life Decay on Past Failures (D-07). Compute decay weight as sum of `2 ** (-delta_days / 7.0)` for all historical failed transactions on matched nodes. If decay weight >= 1.0, apply up to `-15.0` decayed penalty.
   - Step 9: Score Clamping & Decision Gating. Calculate `final_score = round(max(0.0, min(100.0, base_score)), 1)`. Determine decision: `ALLOW` if score >= 70.0, `REVIEW` if 40.0 <= score < 70.0, `DENY` if score < 40.0.
   - Return structured dictionary containing `score`, `decision`, `risk_factors`, `graph_metrics`, and `score_breakdown`.
2. Create `trust-graph-service/tests/test_scoring.py` with comprehensive unit tests:
   - `test_score_brand_new_entity_penalty`: verify brand new fingerprint receives score 90.0 (-10 new entity penalty) and decision `ALLOW`.
   - `test_score_progressive_trust_recovery`: verify buyer with 2 clean transactions has new entity penalty dropped (score 100.0), and with 5 clean transactions receives reputation bonus.
   - `test_score_missing_signals_partial_evaluation`: test fingerprint with only 2 signals receives -5.0 penalty (score 85.0), and 1 signal receives -10.0 penalty.
   - `test_score_known_fraud_direct_node`: mark node `is_known_fraud=True`, verify score drops by 80.0 to 20.0 (`DENY`).
   - `test_score_fraud_neighbor_tiered_subnet_weight`: compare 1-hop fraud neighbor penalty via email (penalty -40.0) vs via IP subnet (penalty -20.0 with 50% tier weight).
   - `test_score_sliding_velocity_windows`: simulate 6 transactions in past 30 minutes, verify -10.0 velocity penalty; simulate 12 transactions, verify -25.0 velocity penalty.
   - `test_score_cross_merchant_spread`: simulate transactions across 4 merchants in 24h (-15.0) and 6 merchants (-35.0).
   - `test_score_ring_membership_forces_zero`: attach `ring_id` to node, verify score drops to 0.0 (`DENY`).
   - `test_score_exponential_decay`: verify a failure from 28 days ago (4 half-lives) has significantly less penalty weight than a failure from 1 hour ago.
</action>

<action>
1. Create `trust-graph-service/app/engine/ring_detector.py` implementing `detect_rings_in_subgraph(graph: nx.Graph, candidate_nodes: set[str]) -> list[dict[str, Any]]`:
   - Return empty list immediately if `len(candidate_nodes) < 3`.
   - Extract induced copy `subgraph = graph.subgraph(candidate_nodes).copy()`.
   - Enforce Criterion 1 (D-11): iterate `nx.connected_components(subgraph)`; skip any component with `len(comp) < 3`.
   - Enforce Criterion 2 (D-11): aggregate all `merchant_ids_seen` across nodes in the component; skip if `len(merchants) < 2`.
   - Enforce Criterion 3 (D-11): calculate average internal degree `sum(dict(comp_sub.degree()).values()) / len(comp)`; skip if average degree < 1.5.
   - Enforce Criterion 4 (D-11): sum `failed_transaction_count` across component nodes; skip if sum < 1.
   - Determine `risk_level`: set to `"CRITICAL"` if `len(merchants) >= 5`, otherwise `"HIGH"`.
   - Resolve Stable Ring UUID (D-12): inspect existing `ring_id` attributes on component nodes; if present, sort and select the oldest canonical UUID; if none present, generate new `str(uuid4())`.
   - Execute Immediate Node Flagging & Metric Aggregation: for every node in component, set `is_known_fraud = True`, `trust_score = 0.0`, and `ring_id = canonical_ring_id`. Collect unique set of failed `tx_id`s across all node transaction histories and sum their `amount_paise` without double-counting.
   - Format Cytoscape elements for the ring: build `nodes` list with `{ data: { id, label, signal_type, signal_value, is_known_fraud: True, trust_score: 0.0, ring_id, merchants_count, transaction_count, failed_transaction_count } }` and `edges` list with `{ data: { id: f"{u}-{v}", source: u, target: v, weight, edge_type, merchants_shared } }`.
   - Return list of detected ring dictionaries containing `ring_id`, `risk_level`, `affected_merchants`, `member_nodes_count`, `blocked_txn_count`, `blocked_amount_paise`, `detection_timestamp`, `detection_algorithm="connected_components"`, and `graph` object.
2. Implement `detect_all_rings(graph: nx.Graph) -> list[dict[str, Any]]` which executes `detect_rings_in_subgraph` across all nodes in `graph.nodes()`.
3. Create `trust-graph-service/tests/test_ring_detector.py` with comprehensive unit tests:
   - `test_ring_rejection_single_merchant`: create 4-node clique with failures but only 1 merchant; assert no ring detected.
   - `test_ring_rejection_insufficient_degree`: create 4-node linear tree spanning 2 merchants with avg degree < 1.5; assert no ring detected.
   - `test_ring_rejection_no_failures`: create high-connectivity multi-merchant component with only successful transactions; assert no ring detected.
   - `test_ring_qualification_success`: create 4-node clique spanning 2 merchants with 1 failure; assert ring detected, nodes marked fraud, `trust_score=0`, risk level `HIGH`.
   - `test_ring_critical_risk_level_five_merchants`: span ring across 5 merchants; assert risk level `CRITICAL`.
   - `test_ring_stable_uuid_merging`: create two ring clusters with existing UUIDs, introduce a connecting bridge transaction; assert merged ring retains the older UUID and all nodes are updated.
   - `test_ring_blocked_amount_deduplication`: verify transactions touching multiple ring nodes only count their `amount_paise` once in `blocked_amount_paise`.
</action>
