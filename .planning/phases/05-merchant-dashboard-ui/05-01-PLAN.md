<threat_model>
ASVS Level: 1
Block on: high severity threats

- Threat T-05-01: Razorpay API Key Secret leakage to client-side browser bundle or browser network inspectors.
  - ASVS Control: V3.1.1 (Cryptographic Key Management), V14.3.1 (Sensitive data in transit).
  - Mitigation: Razorpay Key Secret is sent exclusively from the browser to the internal Next.js Route Handler `POST /api/merchant/verify-keys` and `POST /api/merchant/onboard`. It is never returned in client JSON responses, never stored in localStorage, and encrypted at rest using AES-256-GCM via `encryptMerchantKey()` before writing to `merchants.razorpay_key_secret_encrypted`.

- Threat T-05-02: Live credentials validation bypass allowing invalid or production keys to enter the test-mode environment.
  - ASVS Control: V5.1.1 (Input Validation - key formatting).
  - Mitigation: `POST /api/merchant/verify-keys` strictly validates that `key_id` begins with `rzp_test_`. Requests containing live keys or arbitrary strings are rejected with 422 Unprocessable Entity. The backend executes a server-to-server authenticated test call against `https://api.razorpay.com/v1/payments?count=1` and reports concrete HTTP 401/403/200 status.

- Threat T-05-03: Unauthorized merchant profile modification or session hijacking via forged merchant cookies.
  - ASVS Control: V3.2.1 (Session Management - cookie security).
  - Mitigation: Merchant session cookie `nexus_merchant_id` is validated against existing UUIDs in PostgreSQL `merchants` table. Attempting to switch to an unseeded or non-existent merchant ID returns 404 Not Found.
</threat_model>

<action>
1. Implement `src/app/api/merchant/verify-keys/route.ts`:
   - Accepts `{ key_id, key_secret }`.
   - Validates `key_id` starts with `rzp_test_`. If not, returns 422 with message `"Key ID must start with rzp_test_ for test mode."`.
   - Makes HTTP Basic Auth request to `https://api.razorpay.com/v1/payments?count=1`.
   - If response status is 200, returns `{ valid: true }`. If 401, returns `{ valid: false, error: "Authentication failed with Razorpay API. Verify your test Key ID and Secret." }`.
2. Implement `src/app/api/merchant/onboard/route.ts`:
   - Accepts `{ name, email, key_id, key_secret, initial_products?: Array<{ name, description, price_inr, stock, category }> }`.
   - Generates MaaS Bearer token (`nx_live_*`) and token hash (`hashMaasToken`).
   - Encrypts Razorpay secret using `encryptMerchantKey(key_secret)`.
   - Inserts row into `merchants` table returning `merchant_id`.
   - If `initial_products` provided, inserts products and generates Gemini embeddings using `generateProductEmbedding`.
   - Sets `nexus_merchant_id` session cookie.
   - Returns `{ merchant_id, maas_token: rawToken, catalog_url, transact_url }`.
3. Implement `src/app/dashboard/onboard/page.tsx`:
   - Step 1: Store profile (Name, Email).
   - Step 2: Razorpay Test Credentials (Key ID, Key Secret) with "Validate Keys" trigger calling `/api/merchant/verify-keys`. Displays green checkmark on success or inline Alert on failure.
   - Step 3: Initial Catalog Setup (Quick form to add sample product).
   - Step 4: Progress Indicator ("Preparing catalog for AI buyers...").
   - Step 5: Endpoint Delivery Card:
     - Displays `MaaS Transact URL` (`https://.../api/maas/{merchant_id}/transact`).
     - Masked MaaS Token with copy button.
     - `curl` command snippet showing sample autonomous purchase request.
     - Primary CTA: "Trigger Sample Transaction" button calling simulation test endpoint.
     - Secondary CTA: "Go to Dashboard".
4. Add comprehensive unit and integration tests to `test/merchant-onboard.test.ts` mocking Razorpay HTTP endpoint and verifying database encryption.
</action>
